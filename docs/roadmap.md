# bambiui roadmap and implementation status

Updated: 2026-10-03. This is the **canonical summary of scope, priorities and open product decisions**. [The composer plan](interface-composer-plan.md) expands its implementation gates; [the Studio composer execution plan](studio-composer-execution-plan.md) is the task-by-task implementation checklist (C00–C12) for the confirmed canvas-first direction, with file scopes, decision gates and acceptance tests; [the UX audit](studio-ux-audit-plan.md) is historical evidence, not a second active roadmap. The [accessibility checklist](accessibility-checklist.md) tracks outstanding acceptance. New decisions must update this summary and the affected detailed plan together.

## Direction and decision status

- **Direction:** build on the design-system Studio toward responsive React interface composition. The customizable UI kit is its foundation, not a separate pivot. Figma replacement is a use-case hypothesis to validate, not a shipped capability or a promise to reproduce all Figma features.
- **Confirmed constraints:** local-first editing, real components, shared Light/Dark geometry, versioned documents separate from DesignSystem v3, no arbitrary executable code in page JSON, no requirement to finish every Base UI component first.
- **Free product goal:** no paid tier is required for the current work. Open-source licensing, hosted-service availability/cost limits and support commitments are not decided. Earlier freemium/AI pricing discussion is not a delivery requirement.
- **Not authorized as implementation work:** backend, hosted AI, MCP, cloud collaboration or billing. Supabase is an evaluated candidate, not an adopted dependency.

### Confirmed interaction direction — 2026-10-03 correction

The user explicitly requires a Figma-like workflow **inside the existing Studio**, not a separate form-driven page editor. The sidebar keeps existing components under **Components**, with **Pages** directly below and an Add page action. Selecting a page opens an editable canvas with desktop, tablet and mobile representations. Components, Stack and Grid are inserted and arranged primarily by dragging directly onto that canvas; Layers and keyboard commands are alternatives, not the main authoring surface. The inspector edits the selected instance/layout, separately from global component tokens. Pan/zoom, visible hover/selection, insertion position and parent/slot feedback belong to the main workflow.

The `/examples/page-editor` implementation is an engineering fixture, **not acceptance of the intended UX**. Reuse its validation, commands, history and persistence safeguards; do not continue treating additional form controls or layer-only drag/drop as delivery of the composer. Preserve existing fixture data while introducing the Studio flow.

Base UI Context Menu may supplement visible actions (duplicate, delete, insert layout, wrap in Stack/Grid where valid). It must not be the only action entry point; use the documented `@base-ui/react/context-menu` API and project Base UI guidance.

Delivery order is now: (1) Studio Components/Pages navigation and multiple blank pages, (2) canvas-first insertion/movement and compact instance/layout inspector, (3) responsive editing with web/tablet/mobile representations, (4) selection actions/context menu and keyboard parity, (5) persistence/export and end-to-end task acceptance. Model, safety and test work accompany each slice rather than arriving only at the end. Multiple pages move into the first composer milestone.

**Confirmed frame direction:** the user chose Figma-like independent desktop/tablet/mobile designs; content and structure need not match. A page groups independently editable frame trees using the same component library/design system. Frame-local content, insertion, deletion and layout edits do not implicitly propagate to other frames. Frame duplication can provide a starting point, not an automatic synchronization link. Shared component tokens remain shared; frame-local instance props remain local. Do not mislabel three width previews as this feature. Exact presets, frame-to-runtime breakpoint/export mapping, system deletion/replacement policy and unrelated K1–K5 decisions remain open.

## Product decisions

The English-only Studio uses fixed neutral editor palettes following the selected Light/Dark mode. Header, sidebar, inspector and the outer canvas share #FAFAFA in Light and #202020 in Dark; canvas tools, Develop and portaled dialogs use the same surface family. Editor colors are independent of the user's background and primary colors. Thin borders, spacing and selected states distinguish regions rather than differently tinted panels. The header mark keeps its brand color and semantic status indicators retain their colors. Design-system tokens and export values are unchanged. The existing component Design view displays one theme preview at a time; this does not restrict the planned Pages canvas from showing multiple independent frames together. Use the icon-only Light/Dark switch at the top right of the Design canvas to target manual color editing; Develop keeps the switch in its header to inspect either theme's reference. Non-color edits update both themes, including the shared `fontFamily` preset and `spacingSm`/`spacingMd`/`spacingLg`. There is no editor appearance switch, Compare mode or Scenario context; Develop focuses on code and token references.

The Color builder accepts one brand color. A valid six-digit hex value or preset immediately generates and applies both light and dark global color roles in a single update. Invalid/incomplete input does not change the saved system. Shared numeric values, typography, component overrides and name remain untouched. Existing imported systems with different light/dark sources retain them until a new color is chosen; manual color edits still target the selected theme only.

The studio stores its schema-v3 system locally; v1/v2 migration copies historical values to both themes without recoloring and supplies new preset defaults. Older v3 records without presets receive `system` and 4/8/16px while preserving legacy padding/gap and color values. Curated Google Fonts preset IDs fit the existing schema v3: JSON backups store the chosen ID in both theme records, not remote stylesheets or font files, and Light/Dark continue to share all non-color tokens. Both-theme CSS exports include `--ds-font-family`, `--ds-spacing-sm/md/lg`, raw scale stops, derived colors and system constants; a selected Google preset adds a stylesheet `@import` at the top, before both theme selectors, while `--ds-font-family` holds the resolved stack with local fallbacks. Local presets add no import. Auth, server persistence and account-based saving are not implemented in the current Studio; optional cloud sync is planned for the interface composer, not a prerequisite for local editing. The separate palette CLI still emits raw scales and roles when detailed recipes are needed.

## Planned product direction — design-system-first interface composer

**Current stage: Phase 0, partially implemented.** The Studio canvas remains a specimen viewer. A separate `/examples/account-settings` route renders a validated v1 page fixture through five of the seven components and layout primitives. A separate v1 page bundle pairs a single page with a detached design-system snapshot; JSON import/export and both-theme SSR rendering are tested. It is not a live Studio-system reference or a project schema. Pure page commands and bounded snapshot Undo/Redo are connected to the separate editable/local-save `/examples/page-editor` fixture described below. They are not yet integrated into the requested Studio canvas workflow, and the project/document distribution contract is not complete. See [the composer plan](interface-composer-plan.md) for exact prototype limits.

| Phase | Next deliverable | Completion gate |
| --- | --- | --- |
| 0 — contract and usable output | Resolve K1–K4; connect system data to the page; harden semantic/tree validation; define project backup and portable code delivery. | The same fixture preserves layout/content/theme through JSON round-trip and renderer/export equivalence tests; a clean consuming app uses the delivered sources/styles without rebuilding the layout. Current in-repo TSX type checks alone do not pass this gate. |
| 1 — local-first composer | Studio-integrated Pages below Components; multiple pages, canvas-first component/Stack/Grid insertion and arrangement, web/tablet/mobile editing under the confirmed responsive policy, compact inspector, keyboard alternatives, Undo/Redo and safe local persistence. | One form and one content page survive reload, work at narrow/wide widths and in both themes, and export usable code. No silent overwrite or lost saved edits; the persistence policy for undo history must be explicit. |
| 2 — reuse and broader pages | Broader responsive controls, assets, reusable compositions/instances under the approved K3 contract; add components only as tasks require. | A reused component updates two pages consistently; real users complete the build → export → app-use task. |
| 3 — optional cloud | Only after K5 confirmation: account/snapshot sync, permissions, revision conflicts and optional sharing; provider remains undecided. | Local work remains independent, authorization is tested, and concurrent changes cannot silently overwrite one another. |
| 4 — evidence-led extensions | MCP/AI tooling, collaboration, publishing or prototype interactions only when separately approved. | Each extension has a user need, validated data/permission boundary and acceptable operating cost. |

Accessibility, browser behavior and export fidelity are gates throughout these phases, not work postponed to the end. Dates are intentionally not estimated before scope confirmation.

The existing `output: "export"` frontend and `localStorage` do not supply server endpoints. Retain offline/static editing and assess a separate opt-in sync service before changing the deployment model; choose hosting, storage and auth only after the document/asset/privacy requirements are known. Cloud integration must preserve JSON backups and never silently overwrite concurrent device edits.

## Implemented capabilities

- The active design-system name is editable through the header system selector, which also supports switching, creating, duplicating, deleting and importing systems; Design/Develop links sit beside the logo, with icon-only theme switching and Undo/Redo controls floating over the Design canvas. Seven components (Button, Input, Switch, Checkbox, Card, Badge, Text) with consistent APIs and interactive Design specimens on a pan/zoom canvas with the selected theme's dotted background. Canvas sections show an editor-only outline and selection hint on hover/focus; clicking their noninteractive area selects the related tokens, while drag-to-pan starts only after pointer movement. Fit and zoom controls are available on desktop and retain the Studio font independently of the specimen. At 760px and below, the preview and inspector use natural page scrolling; narrow desktop canvases separate the help and zoom controls to avoid overlap. Actual Card specimens retain their own tokens. Mounted previews retain demo state when switching views or themes.
- Design-only inspector for 32 global tokens and optional per-component overrides; colors are theme-specific, while numeric, typography, component variant border widths and shadow presets are shared. Variant/state color controls expose theme-specific values; contrast warnings navigate to the matching component and state token. The contrast summary appears outside Shape & spacing, highlighting failed checks; details list modeled color pairs and warnings, including manual color failures. On narrow screens, jump links connect the workspace and inspector without adding tabs.
- OKLCH generation of accessible light/dark usage colors from one source, preserving the source in JSON. A safe light brand source can remain the exact primary fill with dark ink; links use derived accessible text ink. The fresh system's primary and the header mark both retain the brand source; editor controls stay neutral. Generated defaults pass 150 modeled color pairs per theme; manual or legacy values may not.
- Develop view with React examples, props/defaults, live aliases, raw color scales, derived values and full CSS, without a token inspector. Copyable snippets are type-checked against real component APIs; they are project examples, not a standalone component package.
- Shared `fontFamily` presets (seven local choices: `system`, `sans`, `humanist`, `serif`, `editorial`, `mono`, `typewriter`; curated Google Fonts choices alongside them) and spacing presets `spacingSm`/`spacingMd`/`spacingLg` (4/8/16px default). Card.Content consumes the corresponding preset for the gap between children at each Card size. The separate layout prototype also uses these variables for Stack/Grid gaps and Container horizontal padding. Legacy `paddingX`, `paddingY` and `gap` globals and component aliases remain independent; no implicit remapping.
- Google Fonts are opt-in: selecting a Google preset triggers browser requests to `fonts.googleapis.com` for CSS and `fonts.gstatic.com` for font files, sharing request data such as IP address with Google. Local choices do not request hosted fonts; offline/blocked remote fonts use local fallbacks. Exported CSS with a Google import can make the same requests for consumers unless they remove it or self-host fonts.
- Export of both-theme CSS (including the resolved font stack, spacing presets and raw color scales) and JSON backup/import, with v1/v2 migration and v3 round-trip. Import resets the generator input to the imported source; token input drafts remount with the imported system.

## Local snapshot page editor prototype

`/examples/page-editor` now provides a separate layer/property editor using the command/history engine: validated insertion, deletion, sibling reorder, cross-parent/slot moves, page rename, text/allowlisted props, Undo/Redo and real-component Light/Dark preview. Session-only Narrow/Wide controls cap containers at 360/960px and available space, not browser breakpoints or native zoom. Interact preserves native controls; Select layers blocks activation and selects the closest valid preview node, with keyboard selection through the Layers list and a no-layout-shift selection outline separate from focus indicators. These preferences are not persisted or exported. It uses a detached default-system account-settings snapshot. Native controls support keyboard operation; preview submissions are prevented. Explicit Save locally persists one validated bundle under a separate versioned key; startup restores without writing. No autosave. JSON backup/import is available; import requires confirmation and does not write storage. Invalid imports preserve state, corrupt storage is preserved and blocks Save until explicit reset, failures retain in-memory edits, and save-time byte comparison guards against silently overwriting another tab's copy (not atomic synchronization). History and drafts remain session-only. No Studio integration, project model, live system link or complete canvas composer is delivered. Desktop native layer drag handles now append to valid different parents/slots using precomputed command-engine-approved targets; local session tokens reject foreign/forged drops. Dragover does not rerun validation; drop/end/Escape clear affordances. Keyboard Move remains available. Touch, drag-based sibling ordering and preview free positioning are not supported. Destination options use command-engine validation, ID-qualified paths and append placement; invalid source/slot/cycle/form/depth outcomes are excluded. Moves retain selection/focus and unapplied property drafts and count as one history step. Nine editing and ten storage tests bring the full suite to 188 passing tests; TypeScript, targeted ESLint and production build passed. `node scripts/page-editor-smoke.mjs` passed twice in disposable Chrome: edits/history/insertion/reorder/deletion, save/reload, invalid import, export Blob content, corrupt storage/reset, 375px overflow and observed runtime/hydration errors. The cross-parent smoke passed 13 check groups, including cross-parent DOM relocation, move undo/redo, selection/focus and destination reset, alongside existing groups including theme/width switching, preview selection, preserved native interaction, keyboard/focus and selection geometry. The latest drag/drop pass preserved 188 passing unit tests and passed TypeScript, full ESLint, build and 15 Chrome smoke groups. Native CDP mouse dragstart/intercepted Chromium drag data/drop verifies successful movement, focus/selection, single-step undo/redo and cleanup; separate synthetic DataTransfer tests verify invalid/forged rejection and no autosave. Actual download completion, visual/assistive-technology acceptance and cross-browser checks remain open; K1–K5 remain unconfirmed.
